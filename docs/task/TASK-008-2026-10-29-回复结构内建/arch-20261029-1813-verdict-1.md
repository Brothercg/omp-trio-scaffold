## 上下文

`bin/init-agent.sh` 的 `create_file()` 对 `install` 失败零跟踪：不计失败、无汇总、收尾退出码恒 0（末句 `printf` 的 rc）。只读目标单件失败时 init 打印噪音后报成功——**静默半部署**。QA 复现：`/tmp/qa-t008/ac2-err.sh`（单件 `install` PermissionDenied → 整体 rc=0 无失败汇总）。spec §6 未裁决「成员件失败是否否决整次 init」，QA 判 `[根因:契约]` contract-gap 停轮，交 ARCH 二选一。

## 候选方案

1. **失败即整体非 0**：任一注入件失败 → 计入失败汇总、收尾明示失败件数与路径清单、整体退出码非 0；注入过程不中断（单件失败不雪崩，其余件照常落）。—— 优点：退出码诚实，自动化/升级脚本可依赖；与 selftest「检出缺失 → FAIL + 整体非全绿」同构；与仓库 fail-closed 文化一致。代价：部分成功的部署也报失败（但状态本就不完整，报失败才是真话）。
2. **尽力而为**：单件报错留痕，整体仍 rc=0。—— 优点：多件部署不因单件失败被判定为失败。代价：**退出码说谎**——「升级静默没发生」只能靠事后 selftest 发现；正是 TASK-006/007 全程与之斗争的静默降级形态；且与 spec §6「非 0 退出」字面读法相悖，需反向改约。

## 决策

选定**方案 1（失败即整体非 0）**，并明确过程语义：**过程尽力、结果硬**——单件失败不中断后续注入，收尾汇总「失败 K 件 + 路径清单」，`K > 0` 即 exit 1。理由：init 是门禁的信任面入口（下游升级靠它搬运门禁件），半部署 + rc=0 的唯一防线只剩事后自检，而退出码是自动化的唯一信号；诚实退出码优先于「看起来成功」。

## 后果

- **契约**：spec §6 修订（v2）载明上述语义，v1 的「非 0 退出 + 明示路径」按本裁决读作整体层。
- **实现（dev 修复项，bin/** 走无角色窗口）**：
  1. `create_file()` 任一失败路径（`install`/`mkdir` 非 0）→ `FAILED` 计数 + `失败  <相对路径>：<原因>` 明示；失败**不得**计入 `CREATED`/「覆盖」。
  2. 收尾汇总追加失败件数与路径清单；`FAILED > 0` → exit 1；全成功 rc=0。
  3. 回归：read-only 目标 → rc=1 + 汇总含该路径；全绿路径 rc=0 且「失败 0 件」。
- **否决方案及理由**：见候选 2——rc=0 与「非 0 退出」契约字面冲突，且复刻静默降级反模式。

## 推翻条件

若 init 转型为「多次增量同步工具」（单件失败属常态、需容忍），再审本裁决；届时应引入 `--best-effort` 显式开关而非改默认语义。
