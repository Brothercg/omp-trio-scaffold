## 1. 缺陷现象

`v0.2.0` 发布过程中，`TASK-001` 交付的 `pre-push` 与 `trio-guard` 暴露出
6 项契约未覆盖的行为。最直接的一项是 G-2：引入门禁的任务本身无法通过
该门禁，最终推送只能以「未设置 `TRIO_ROLE`」的人工方式完成。

| 编号 | 级别 | 实际行为 | 证据指针 |
|---|---|---|---|
| G-1 | Major | 只读 / 索引命令被当作写入拒绝：Bash 中执行 `bun tests/trio-policy.test.mjs`、`grep ... tests/...`、`git add -- ...` 均被 `trio-guard` 以「不得写入 `tests/**`」拦截；改用 `/tmp` 路径清单 `git add --pathspec-from-file` 则可绕过同一拦截 | `.omp/hooks/pre/trio-guard.ts` Bash 分支；§3 输出 1、2 |
| G-2 | Critical | 自举 / 维护任务没有 `qa-*-report-*.md`，`TRIO_ROLE=dev` 执行 pre-push 返回 1；`TASK-001` 的看板已是 `user_signed` 也无法放行 | `templates/pre-push` 的 dev 分支；§3 输出 3 |
| G-3 | Minor | `profiles/*.rules.md` 已更新而 `.omp/trio/*.rules.md` 仍旧；此时 `trio-policy` 111 项仍全绿，无断言守护 | `profiles/` 与 `.omp/trio/` 双份文件；§3 输出 4 |
| G-4 | Minor | `trio-selftest.sh` 硬编码 3 个 suite，新增的 `trio-pre-push.test.mjs`（13 项）不被执行；`init-agent.sh` 也只部署 3 个测试 | `bin/trio-selftest.sh` suite 数组；`bin/init-agent.sh` 第 6 段 |
| G-5 | Minor | 仓库无 `CHANGELOG.md` / `VERSION` / `package.json`；版本号只存在于 README 散文与 tag。`v0.2.0` 靠手改 README + tag message 充当 changelog；policy / ADR 却引用 `CHANGELOG.md`、`pyproject.toml` | `README.md` 版本行；`.omp/trio/policy.txt`；`ADR-0001` |
| G-6 | Major | pre-push 的 `REPORT_GLOB` 为全仓库 `docs/task/*/qa-*-report-*.md`，看板用 `ls -t ... \| head -1` 取 mtime 最新；`AC-7` 未要求报告 / 看板绑定本次推送的任务或提交 | `templates/pre-push` 的 `REPORT_GLOB` / `newest_board` |

- **实际行为**：见上表；全部为本次发布中的实测结果。
- **期望行为**：G-1 只读命令不应触发写门禁；G-2 维护 / 自举任务应有机器可读、
  可审计的放行路径；G-3/G-4 单一真值源应被生成或断言；G-5 发布元数据应有
  单一真值源；G-6 放行证据应与待推任务 / 提交绑定。
- **复现概率**：G-1、G-2、G-4、G-5、G-6 必现；G-3 在只改一侧时必现
  （`v0.2.0` 发布前已实际发生，发布时手工 `cp` 修复）。

## 2. Failing Test Script

类型为 `contract-gap`，按 `templates/bug.template.md` §2，最小复现脚本仅对
`type: code` 强制。本次不新增 `tests/**` 文件（DEV 写权不覆盖），改用可
独立执行的命令复现；每条都只读或只影响索引。

```bash
# G-1：同一测试文件，两种调用方式结果不同
bun tests/trio-policy.test.mjs          # 被 trio-guard 拦截（不得写入 tests/）
cd tests && bun ./trio-policy.test.mjs  # 通过 111/111

# G-2：自举任务在 dev 身份下无法推送
TRIO_ROLE=dev bash .git/hooks/pre-push </dev/null   # exit 1

# G-3：两侧角色简报是否一致
diff -q profiles/dev.rules.md .omp/trio/dev.rules.md

# G-4：自测套件与实际测试文件
grep -n 'trio-.*\.test\.mjs' bin/trio-selftest.sh
ls tests/*.test.mjs

# G-5：发布元数据真值源
ls CHANGELOG.md VERSION package.json 2>&1

# G-6：放行证据的选择逻辑
grep -n 'REPORT_GLOB\|newest_board' templates/pre-push
```

## 4. 最小复现步骤

1. 在 `v0.2.0`（commit `7e84902`）的工作树中，以 `TRIO_ROLE=dev` 启动会话。
2. 执行 `bun tests/trio-policy.test.mjs` → 观察 G-1 拦截。
3. 执行 `TRIO_ROLE=dev bash .git/hooks/pre-push </dev/null` → 观察 G-2，exit 1。
4. 将 `profiles/dev.rules.md` 增加一行、不改 `.omp/trio/dev.rules.md`，再跑
   `trio-policy` 测试 → 观察 G-3，测试仍全绿。
5. 阅读 `bin/trio-selftest.sh` 的 suite 数组与 `tests/` 目录 → 观察 G-4 不一致。
6. 执行 `ls CHANGELOG.md VERSION package.json` → 观察 G-5 三者皆缺。
7. 阅读 `templates/pre-push` 的 `REPORT_GLOB` 与 `newest_board` → 观察 G-6
   选择范围是全仓库 / mtime，而非本次推送对象。

## 5. 影响面

- **G-1**：高频误伤——测试、检索、暂存都要换写法；更严重的是同一套文本匹配
  可被 `/tmp` 路径清单绕过，形成「合法的读被拦、越权的写能过」的双向偏差。
- **G-2**：门禁自举悖论——发布门禁无法由引入它的任务自身满足，只能 `unset`
  人工放行；该动作无角色、无报告、无审计记录，恰好绕过了刚建立的发布链。
- **G-3**：运行时行为与出厂源可能长期不一致；本次靠人工发现，测试无感知。
- **G-4**：`trio-selftest` 的「门禁全部生效」结论不覆盖新增发布门禁；目标项目
  也拿不到该回归套件。
- **G-5**：发版依赖记忆与手工，`policy` 引用的文件不存在，规则与现实脱节。
- **G-6**：发布证据可被旧任务的全绿报告 + 任一 `qa_passed` / `user_signed` 看板
  满足；`git checkout` 会改变 board 的 mtime，选择结果不稳定。
- **可绕过性**：G-1、G-2、G-6 均可绕过（分别为 pathspec 文件、`unset`、旧证据）；
  G-3~G-5 不是绕过问题，而是可维护性 / 可复现性问题。
- **数据损坏**：无；不涉及业务数据。

## 6. 建议的修复方向（仅建议，不代劳，不构成 AC）

> 以下只指出位置与可选方向；是否采纳、如何写成 AC、优先级由 ARCH 裁决。

| 缺口 | 疑似位置 | 建议方向 | 需 ARCH 决定的问题 |
|---|---|---|---|
| G-1 | `.omp/hooks/pre/trio-guard.ts` Bash 分支 | 读命令白名单（`git diff/log/status`、`grep`、`bun test` 等）；只解析重定向 / 写动词；`git add` 交给 pre-commit；签名化 pathspec 清单或禁止其绕过 | 门禁的边界是「文件写入」还是「命令意图」？是否接受少量绕过以换取低误伤？ |
| G-2 | `templates/pre-push` dev 分支；`board.md` | 看板增加机器可读字段（如 `release_exempt: maintenance`），pre-push 校验并输出审计行；或引入显式 maintainer 身份 | 自举 / 维护任务是否需要独立角色？豁免是否必须留痕？ |
| G-3 | `profiles/`、`.omp/trio/`、`tests/trio-policy.test.mjs` | 由 `profiles/` 生成 `.omp/trio/` 副本，或增加相等断言 | 运行时副本是生成物还是可手改的第二真值源？ |
| G-4 | `bin/trio-selftest.sh`、`bin/init-agent.sh` | suite 自动发现 `tests/*.test.mjs`；init 全量部署测试文件 | 目标项目是否应携带全部回归测试？ |
| G-5 | 仓库根、`bin/` | 引入 `VERSION` + `CHANGELOG.md` 或 `bin/trio-release.sh`，统一 bump / 截版 / tag / 校验 | 本仓库的版本真值源选哪一个？是否要求发布脚本先跑全绿？ |
| G-6 | `templates/pre-push`、`board.md` | 报告基线 commit 必须是待推提交的祖先；看板显式引用 `qa-*` 报告路径；状态行用机器字段而非 Markdown 表格 | 放行粒度绑定任务、分支还是 commit？看板格式是否允许升级？ |

**DEV 建议的优先级（供参考）**：P0 = G-2、G-1、G-6；P1 = G-4、G-5；P2 = G-3。
理由：G-2 使发布链只能靠后门收尾；G-1 误伤所有读操作且存在静默绕过；G-6 是
真实的错误放行面。G-4 / G-5 影响可复现性，G-3 属维护性重复。
