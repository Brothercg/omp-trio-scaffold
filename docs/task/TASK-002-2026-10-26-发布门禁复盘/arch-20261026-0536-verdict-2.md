## 1. 分歧点

DEV 在 implementing 首步被写策略拒绝：spec §8 分派的 5 个文件（guard.ts、
pre-push、board.template.md、selftest、init-agent）对 DEV 全部不可写——
`.omp/hooks/**` 与 `bin/**` 是 `deny *`（deny 优先，追加 allow 无效），
`templates/**` fail-closed。DEV 提出 4 个问题：谁写、policy 以何语义放行、
门禁自保可否按任务豁免、豁免如何留痕与回收。

## 2. 判定

**BUG-002 成立，定性：契约缺陷（spec §8 与 policy 真值源冲突——分工写了
执行人，没写执行通道，是 ARCH 的契约漏洞，非 DEV 实现问题）。**

### A. 这 5 个文件由谁写？——仍由 DEV，经任务级临时写通道

| 文件 | 写者 | 身份 | 依据规则 | 通道形态 |
|---|---|---|---|---|
| `.omp/hooks/pre/trio-guard.ts` | DEV | `TRIO_ROLE=dev` | ADR-0003 任务级写窗口 | 临时 `allow dev`（单文件，无通配） |
| `templates/pre-push` | DEV | 同上 | 同上 | 同上 |
| `templates/board.template.md` | DEV | 同上 | 同上 | 同上 |
| `bin/trio-selftest.sh` | DEV | 同上 | 同上 | 同上 |
| `bin/init-agent.sh` | DEV | 同上 | 同上 | 同上 |

**为什么不由 ARCH / 用户代施（DEV 选项 B）**：TASK-001 是门禁自举且当时无
DEV 会话，维护者代施合理；TASK-002 有完整 DEV，代施将同时造成 ①契约 §8
推倒重写、②diff 失去角色溯源（用户既实现又终验 = 元层面「自己给自己判卷」）、
③用户成为实现瓶颈。QA 独立验证不受影响的前提下，实现者角色分离的收益保留。

**为什么不是永久 allow（DEV 选项 C）**：被约束者获得永久门禁改写权，直接
违反门禁自保语义，一票否决。

### deny 优先级的处理（关键技术点）

DSL 无「deny 中的例外」表达力，且 deny 优先 → `deny *` 存活时任何 allow
无效。唯一语义正确的解法：**把两条目录级 `deny *` 在窗口期内降为角色级
deny（arch / qa），DEV 侧交由 fail-closed 兜底 + 精确 allow 放行**：

- dev 写 `.omp/hooks/pre/trio-guard.ts` → 命中窗口 allow → 放行
- dev 写 `.omp/hooks/pre/其他文件` → 无 allow，fail-closed → 拒绝
- arch / qa 写两棵树下任意路径 → 角色级 deny → 拒绝
- **根信任两行永不动**：`deny * .omp/trio/policy.txt`、`deny * .git/hooks/pre-commit`
  窗口内外都是 `deny *`。DEV 的窗口**不包含**策略真值源与 pre-commit
  模板/已部署件——即使 guard.ts 被塞后门，pre-commit 在提交时仍按
  policy.txt 权威判定（ADR-0002 三层效力模型的兜底层）。

### B. 分路径结论

| 路径 | 现状 | 结论 |
|---|---|---|
| `templates/**` | fail-closed（非显式 deny） | **不改 deny 语义**；窗口内加 2 条精确 `allow dev`（pre-push、board.template.md）；`templates/pre-commit` 维持所有角色不可写——权威层保持不可触 |
| `.omp/hooks/**` | `deny *` | **窗口期改为** `deny arch` + `deny qa`（dev 走 fail-closed + 精确 allow）；回收后恢复 `deny *` |
| `bin/**` | `deny *` | 同上 |
| `.omp/trio/policy.txt`、`.git/hooks/pre-commit` | `deny *` | **永久维持，不参与窗口** |

**是否需要任务级临时通道：是**。但只能以「policy 注释块 + 精确单文件
allow + 写死的回收条款」表达——DSL 无法表达到期语义，而给 DSL 加
task-scoped 指令需要先改 guard.ts / pre-commit，是自举悖论（要开门才能
造钥匙）。程序性控制补足机器缺口。

### 裁决 DEV 的 4 问

1. **谁写**：DEV 写，见 A 表。
2. **哪几条、何语义**：见下方 §4 的 policy diff——deny 降角色级 + 5 条
   精确 allow，注释块锚定裁决编号与回收条件。
3. **门禁自保可否豁免**：可，但仅限**门禁自举/维护类任务**、仅限**派生
   执行件**（guard / 模板 hook / 自检脚本），根信任（policy.txt、
   pre-commit）**永不豁免**；豁免必须以本裁决 + ADR-0003 为据。
4. **裁决前 DEV 行为**：保持 `blocked`，不实施、不绕过（DEV 已正确执行）。

## 3. 依据

- policy.txt 判定语义原文：「任一 deny 命中 → 拒绝；否则任一 allow 命中 →
  允许；否则拒绝（fail-closed）」——deny 优先是既有契约语义，本裁决不改
  语义本身，只改 deny 行的作用域（角色级）。
- BUG-002 §3 的 5 条 `decide()` 输出与 ARCH 复核一致（deny 命中 3 条、
  fail-closed 2 条）。
- ADR-0002 §决策 1：guard 尽力而为、pre-commit / pre-push 权威——DEV 窗口
  触及 guard.ts 是「尽力层」，权威层（pre-commit 模板与已部署件、policy.txt）
  不在窗口内，防线未破。
- ADR-0002 §决策 2：`unset TRIO_ROLE` 禁用于 agent 会话、maintainer 角色
  已否决——本裁决两条红线均未触碰。
- 门禁自保注释「否则被约束者可以自行解除限制」：窗口期间 DEV 可改 guard.ts
  确实削弱该保护，由三重补偿兜住：①QA 独占 tests/**（DEV 改不了验证面）、
  ②pre-commit 权威层不可触、③用户终验签字前逐 diff 审查。残留风险见
  ADR-0003 §后果。

## 4. 处置

### 4.1 policy.txt 精确 diff（交用户以无角色身份落盘）

替换文末「门禁自身的保护」整段（原文 4 行 `deny *`）为：

```diff
 # ─────────────────────────────────────────────────────────────────────────────
-# 门禁自身的保护：任何角色都不得改写门禁逻辑或策略
-# （否则被约束者可以自行解除限制）
+# 门禁自身的保护：策略真值源与权威关卡绝对禁改
+# （否则被约束者可以自行解除限制）
 # ─────────────────────────────────────────────────────────────────────────────
-deny * .omp/hooks/**
 deny * .omp/trio/policy.txt
 deny * .git/hooks/pre-commit
-deny * bin/**
+
+# 门禁派生执行件（guard / 模板 hook / 自检脚本）：维护窗口内对 DEV 开放
+# 单文件写权；其余角色、其余路径一律拒绝（deny 优先 + fail-closed）。
+deny arch .omp/hooks/**
+deny qa .omp/hooks/**
+deny arch bin/**
+deny qa bin/**
+
+# ── BEGIN TASK-002 临时写通道（arch-20261026-0536-verdict-2.md / ADR-0003）──
+# 回收条件：TASK-002 看板推进到 user_signed 后，用户 MUST 整段删除
+# BEGIN/END 之间内容，并把上方四条角色级 deny 恢复为：
+#   deny * .omp/hooks/**
+#   deny * bin/**
+# 回收动作记入看板决策记录；QA 按 spec AC-12 核验。
+allow dev .omp/hooks/pre/trio-guard.ts
+allow dev templates/pre-push
+allow dev templates/board.template.md
+allow dev bin/trio-selftest.sh
+allow dev bin/init-agent.sh
+# ── END TASK-002 临时写通道 ─────────────────────────────────────────────────
```

## 5. 后果

- 正面：TASK-002 的 8 项 AC 全部有了合规实现入口；角色分离保留（ARCH 契约
  / DEV 实现 / QA 验证）；根信任两文件全程不可触，权威层防线未动。
- 负面与残留风险（接受并记录）：
  1. 窗口期 DEV 经 bash 写意图通道写 `.omp/hooks/**` 其它路径时，guard 的
     deny 列表对 dev 不再含这两棵树 → 实时拦截降级。补偿：pre-commit
     fail-closed 使未授权文件**进不了历史**（落盘可、提交不可），终验前
     diff 审查兜底。与 ADR-0002「guard 尽力而为」定位一致。
  2. `init-agent.sh` 是部署件，被塞后门可影响未来 init 的 hook 部署。
     补偿：QA 测试 + 用户终验逐 diff；已部署 `.git/hooks/pre-commit` 不受
     影响（deny *，窗口不触）。
  3. 回收依赖人工步骤。补偿：AC-12 硬性核验 + 看板决策记录强制留痕。
- **推翻条件**：窗口期内发生一次越权写入或后门尝试 → 立即回收窗口，
  改走「用户代施」（DEV 选项 B），并重新评估门禁 DSL 是否需要到期语义。
- 同类问题判例：契约分派文件写权时，MUST 同时核对 policy 真值源的可写性；
  「谁做」与「凭什么能做」是契约的两个必备面，缺一即 contract-gap。
