# ADR-0014 根信任与门禁任务落地：无角色执行窗口 + ARCH 执行提示词

- 状态：accepted
- 日期：2026-10-29
- 关联：`ADR-0003`（门禁自举临时写通道）、`ADR-0012`（威胁模型「防呆不防恶」）、`TASK-007`（首个执行实例）

## 1. 上下文

ADR-0003 的通道执行模型要求：用户手工落盘 policy 窗口 diff、DEV 起草补丁、ARCH 代施、用户逐件部署。TASK-007 这类门禁/根信任任务里，人工逐件落盘是吞吐瓶颈，「DEV 起草 → ARCH 代施」的双人接力也是摩擦点。用户 2026-10-29 决定：此类任务统一改由一个**无角色 omp 窗口**按 ARCH 产出的执行提示词批量执行，此后同类任务照此办理。

## 2. 候选方案

1. **无角色执行窗口 + ARCH 执行提示词**：ARCH 出自包含提示词（上下文 + 铁律 + 分步 + 完成判定），用户开一个不设 `TRIO_ROLE` 的 omp 窗口执行，QA 事后对抗复测。
2. 维持 ADR-0003 执行分工：用户逐件落盘 + DEV 起草 + ARCH 代施。
3. 用户手工逐件改。

## 3. 决策

选定 **方案 1**。涉及根信任 / 门禁自保面的任务，落地流程统一为：
**ARCH spec（契约）→ ARCH 执行提示词 → 用户无角色窗口执行 → QA 对抗复测 → 用户终验回收**。
执行提示词 MUST 含四要素：自包含上下文（路径 + 依据文件）、铁律（禁 push、显式 pathspec、限定文件清单、真实输出）、分步实施（对齐 spec 章节）、完成判定（可检查）。ADR-0003 的**窗口形态不变**（policy 注释块 + 精确单文件 allow + 回收条件），变的是执行主体：窗口内文件由无角色执行窗口直接实现，不再经「DEV 起草 → ARCH 代施」接力。

## 4. 被否决方案及理由

- **方案 2**：双人接力 + 人工逐件落盘，正是本决策要消除的摩擦；TASK-007 上已试拆（dev-*.md 内联 diff 代施）证明成本高于收益。
- **方案 3**：用户从终验者退回执行者，违背 HITL 分层（`qa_passed → user_signed` 的签字人不应是实现人）。

## 5. 后果

- **正面**：用户回归终验者本位；门禁任务一次性批量落地；提示词本身即审计件（可存档、可重放）。
- **负面 / 缓解**：
  - 无角色窗口无写权隔离（guard 对其全放行）→ 按提示词铁律 + 显式 pathspec commit + QA 复测 + git 历史审计补偿；与 ADR-0012「防呆不防恶」一致。
  - 执行质量依赖提示词完备性 → 提示词四要素为硬要求，ARCH 对完备性负责。
- **推翻条件**：执行窗口发生误改/越权（误伤真实出现一次即回收）→ 回退 ADR-0003 方案 1 人工通道并重审本决策。
