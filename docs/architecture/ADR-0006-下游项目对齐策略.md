# ADR-0006 下游项目对齐策略（C+A：结构对齐 + 逃生舱）

- 状态：accepted
- 日期：2026-10-27
- 关联：ADR-0000（架构总览）、ADR-0002/0003（policy 根信任与逃生舱流程）
- 决策来源：grill-me 对齐会话 `downstream-adapt`（7 问全解）

## 1. 上下文

脚手架服务于用户自有的一组项目。下游项目的目录结构可能与脚手架设计
（`docs/task/`、`docs/architecture/`、`src/`、`tests/` + Python/Node 公共维护区）
存在较大差距，需要适配策略。约束：

- 用户可调度下游项目，改造成本由用户承担（非外部转嫁）；
- 「流畅最大化」是目标，需可判定度量；
- policy.txt 是 `deny *` 根信任，改写只能走用户人工落盘 + ARCH 核验
  （TASK-003 B-1 已验证）。

## 2. 候选方案

1. **A：policy.txt 按下游定制** —— 优点：零新代码、已验证；缺点：每项目人工 diff，
   升级时方言漂移。
2. **B：init-agent.sh 参数化布局（--layout 模板集）** —— 优点：预设一条命令；
   缺点：模板面是持续维护成本，每布局一分方言。
3. **C：下游朝脚手架标准布局对齐** —— 优点：单真值源、工具零分支、升级传播、
   审计一致全量兑现；缺点：存量项目需一次性迁移。
4. **D：双层 policy（policy.local.txt 覆盖层）** —— 优点：升级不破坏定制；
   缺点：破坏单真值源，为未发生的升级冲突过度设计。

## 3. 决策

选定 **C+A**（结构对齐为主，人工落盘通道为逃生舱），并定义四组配套口径：

### 3.1 度量（M1 / M3 为主，M2 缓）

- **M1 零手工 diff**：init ≤2 条命令后三角色可干活，无人工改文件；
- **M3 语义零漂移**：下游 policy.txt 与上游逐字节相等（逃生舱项目除外）；
- M2（升级不破坏）缓行——升级冲突未真实发生，不为它引入双层 policy。

### 3.2 标准布局（S1：本项目即标准）

标准 = 脚手架当前结构逐字为准：`docs/task/TASK-<NNN>-<YYYY-MM-DD>-<slug>/`、
`docs/architecture/`、`src/`、`tests/`、Python/Node 公共维护区 + 现 policy.txt
glob。不另写抽象规范；判断「对齐完成」的尺 = `trio-align --check` 零差异。

### 3.3 存量迁移（X3：自动迁移 + 默认 dry-run）

`bin/trio-align.sh`：检测差异 → `git mv` 迁目录 + 全仓引用清扫 → 输出核验报告。
默认 `--dry-run`，正式执行需显式确认。核验复用 TASK-003 AC-10 口径：
逐行 diff 审，路径字符串外零改动。

### 3.4 升级同步（U1：分类覆盖）

- 执行件（`.omp/hooks/**`、`bin/**`、`templates/**`）升级直接覆盖——门禁自保
  `deny *`，无角色改过，覆盖零风险；
- `policy.txt` 与上游有 diff 时提示不覆盖、人工核对，保留逃生舱痕迹。

### 3.5 验收口径（可判定）

「init ≤2 条命令 + `trio-selftest --fast` 全绿 + `trio-align --check` 零差异 +
policy.txt `cmp` 逐字节相等」（逃生舱项目除外，其 policy diff 行必须在项目
README 或 board 标注原因）。

## 4. 后果

- 正面：单真值源/工具零分支/心智模型统一/任务产物互操作/升级传播/审计一致
  六项系统性好处全量兑现；B 模板面取消，维护面为零。
- 负面：存量项目一次性迁移成本（由 `trio-align.sh` 自动化 + dry-run 刹车兜底）；
  异形项目（monorepo 内嵌子仓等）走逃生舱时存在局部差异，需标注。
- 推翻条件：出现用户无法调度的第三方仓必须集成（B 复活）；或升级冲突真实
  高频发生（D 复活、M2 升级为主度量）。
