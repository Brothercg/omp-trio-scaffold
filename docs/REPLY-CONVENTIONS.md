# 三角色回复与产物引用规范

> 单一真值源：ARCH / DEV / QA 的**聊天回复**与**非报告产物** MUST 遵循本文件。
> 依据：`docs/architecture/ADR-0004-三角色回复规范与任务接力机制.md`、
> `docs/architecture/ADR-0005-任务命名流程标记与接力提示词.md`。
> 优先级：`qa-*-report-*.md` 的法定格式以 `templates/report.template.md` 与
> `bin/trio-check-report.mjs`（T1–T10）为准，本文件不适用；冲突时报告格式优先。

## 1. 适用范围与优先级

- 适用：三角色的聊天回复；`dev-*` / `arch-*` 非报告产物的引用与摘要写法。
- 不适用：`qa-*-report-*.md`（法定格式见模板与校验器，冲突时报告格式优先）。
- 修订：见 §7。

## 2. 结论表（回复开头，先结论后细节）

每份角色回复 MUST 以结论表开头，之后才是解释性行文——**先讲结论，再简要阐述细节**。

| 字段 | 含义 |
|---|---|
| 结论 | 一句话：本步完成了什么 / 判定了什么 |
| 状态 | 看板态（`implementing` / `testing` / `qa_passed` / `blocked` / `waiting_user` / …） |
| 未完成项 | 有则逐条列（含失败 / 挂起），无则写「无」 |
| 产物 | 本步产出的完整相对路径（见 §4） |

目标：用户能在 5 秒内从任一角色回复读出「做完没有、卡在哪」。

## 3. 失败 / 未完成项解释

失败与未完成项逐条填下表（开发失败、测试失败、裁决挂起用同一套字段——
差异在内容，不在字段名）：

| 字段 | 含义 |
|---|---|
| 条目 | 哪条 AC / 什么操作（如 `AC-9r`、`bun tests/x.test.mjs`） |
| 期望 / 实际 | 期望值与实际值 |
| 复现 | 命令或最小步骤（DEV 贴失败测试名，QA 贴复现脚本路径） |
| 根因 | 已定位写结论；未定位写「未定位 + 当前假设」 |
| 解除条件 / 下一步 | 谁做什么能转绿：挂起项填解除条件，缺陷填修复责任方 |

## 4. 路径规范

- 任务目录形态：`docs/task/TASK-<NNN>-<YYYY-MM-DD>-<slug>/`；产物引用 MUST 写
  从项目根起的完整相对路径（如
  `docs/task/TASK-003-2026-10-26-回复规范落地/arch-20261026-1248-spec.md`）；
  禁止裸文件名、禁止绝对路径与 `~`、禁止省略号缩写；路径避免含空格。
- 完整路径首次出现（可点击），后文可用短名指代。
- 轮次约定（身份不可变，轮次走自由段）：QA 复测报告主题必带 `-第<N>轮` 后缀
  （如 `qa-<…>-report-<主题>-第2轮.md`）；DEV 迭代交付带 `-第<N>轮`
  （如 `dev-<…>-release-第2轮.md`）；首轮可不带。
- qa 报告内的反引号路径由校验器 T10 机械核验存在性。

## 5. 下一步任务分配块（回复结尾）

任务未闭环时，回复 MUST 以「下一步任务分配」结尾：每个**当前可执行**步骤一段——
`**承接方：<角色>**` 行 + ` ```text ` 围栏完整提示词块（直接复制即用）。
提示词块必含七段（段名固定）：

【任务】TASK-00N-<slug> · <本轮目标>（第 N 轮）
【必读】<完整相对路径> —— <读它干嘛>
【指令】1. <动作，含改哪个文件的哪类内容 / 跑什么 / 裁决什么> 2. …
【交付】<产物落位与命名>（轮次后缀按 §4）
【纪律】<红线：不可越权路径、commit 显式 pathspec、…>
【突出】必须重启窗口 / 会话才能执行下一步（无则删本段）
【完成】<做到什么算完> + <回写 board 哪一段>

`【突出】` 段存在时，回复 MUST 在围栏外以**红色**独立告警行重复该前置
（形如 ⚠ **必须重启窗口 / 会话才能执行下一步**，红字渲染用 `\textcolor{red}{...}`），
围栏内【突出】原文保留供承接方阅读——告警给用户看，原文给承接方用。

约束：

1. 看板状态 ≠ `user_signed` **或挂起清单非空**时 MUST 以分配块结尾；真闭环才写
   「任务闭环，无接力」。
2. **按需生成不预支**：只发当前可执行步骤的完整块，并行可执行才多块（各承接方
   一块）；后续步骤不预写（会失真），全局图景归 board「处置流程」段。
3. 同轮同步进 board 交接备注，board 为权威；冲突以 board 为准（会话重启后从
   board 重建接力）。
4. `blocked` / `waiting_user` 态「承接方」= `用户`，【指令】写明待裁决点。

## 6. 挂起清单与集中补测

挂起清单是 board 的结构化段（见 `templates/board.template.md` §7），字段：

| 字段 | 含义 |
|---|---|
| 条目 | AC 编号或操作名 |
| 解除条件 | 可判定的未来事实 |
| 触发者 | 条件成熟后谁负责跑补测 |
| 解除后动作 | 精确命令或步骤 |

规则：

1. 每轮回复合盘：未清零挂起项 MUST 出现在结论表「未完成项」。
2. 解除条件成熟 → 触发者下一轮一次跑完所有已成熟项（集中补测轮），结果进
   qa 报告 / 看板；不逐项零敲碎打。
3. `user_signed` + 挂起清单清零 = 真闭环。

## 7. 修订流程

本文件是活文档。修订由任一角色提出 → 记 board 决策记录；跨任务语义变更须出 ADR；
schema 变更 MUST 同步 `templates/` 与 `tests/` 对应断言后方可合入。
